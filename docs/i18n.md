# Internationalization (i18n)

How FOSScore is translated, and the complete workflow for the repository owner: managing
languages, synchronizing them with Crowdin through the `l10n_dev` branch, and getting a free
Crowdin open-source license.

Everything in this work stream — code, comments, string keys, commit messages, branch names and
this document — is written in English.

- **Branch:** `feature/i18n-string-resources` (from `main`)
- **Status (2026-10-11):** all user-facing strings extracted; English default; Spanish and French
  translations; in-app language picker; Crowdin configuration and workflow committed but inactive
  (no Crowdin account yet).

## 1. Overview

```
 developers                      GitHub                               Crowdin
 ──────────                      ──────                               ───────
 edit values/strings.xml ──PR──▶ main ──(workflow: upload sources)──▶ source strings
                                                                        │ translators
                                                                        ▼
                                 l10n_dev ◀──(workflow: download)──── translations
                                    │
                                    └──PR "New Crowdin translations"──▶ main (owner reviews, merges)
```

- `values/strings.xml` (English) is the **only** file developers edit.
- `values-<lang>/strings.xml` files are **owned by Crowdin** once it is connected; they arrive
  through the `l10n_dev` branch and a pull request into `main`.
- The workflow lives in `.github/workflows/crowdin.yml`; the file mapping in `crowdin.yml`.

### Files

```
app/src/main/res/
  values/strings.xml       English: default language and Crowdin source
  values-es/strings.xml    Spanish
  values-fr/strings.xml    French
app/src/main/java/.../locale/LocaleHelper.kt     language selection (SUPPORTED list)
app/src/test/java/.../locale/LanguageResourcesTest.kt
crowdin.yml                                      Crowdin file mapping (no credentials)
.github/workflows/crowdin.yml                    Crowdin sync workflow (l10n_dev → PR into main)
```

Plain language folders (`values-es`, not `values-es-rES`) are used on purpose: they also cover the
regional variants of the phone language (es-MX, fr-CA…). A genuinely regional translation, if ever
needed, uses the BCP 47 folder form `values-b+pt+BR`.

## 2. How the app picks its language

Modelled on AndroidAPS' `LocaleHelper` (`core/ui/.../locale/LocaleHelper.kt` in AAPS):

| Piece | Role |
| --- | --- |
| `locale/LocaleHelper.kt` | `SUPPORTED` language list, reads the preference, builds the locale, `wrap(context)` |
| `Settings.language` / `setLanguage` | Preference `language` in `fosscore_settings`; `"default"` = follow the phone |
| `MainActivity.attachBaseContext` | Wraps the base context with the chosen locale |
| `MainActivity.changeLanguage` | Stores the new choice and calls `recreate()` |
| `LibraryScreen` → `LanguageMenu` | Picker in the library header: "System default" + one entry per supported language |

- **System default (`"default"`)** — the context is left alone; Android picks the best
  `values-<lang>` folder for the phone's language list, and falls back to English.
- **Explicit choice** — `wrap()` builds a configuration context with that locale, so every resource
  lookup in the activity (Compose `stringResource`, Material's own strings) uses it.
  `Locale.setDefault` is updated as well so numbers and `String.format` match the UI.
- Switching back to "System default" restores the phone locale read from
  `Resources.getSystem().configuration` (not `Locale.getDefault()`, which `wrap()` overwrites).
- Picker entries are autonyms from `Locale.getDisplayName(locale)` ("Español", "Français"), so a
  new language needs no extra string.

Differences from AndroidAPS:

- Only `Configuration.setLocale` is used (the single-locale form), no `LocaleList`.
- No "simple mode" override and no `dk` → `da` fix-up: the list holds valid BCP 47 tags only.
- No settings screen yet, so the picker sits in the library header.

App Bundles: `bundle { language { enableSplit = false } }` in `app/build.gradle.kts`. Without it,
Google Play installs only the translations matching the phone's languages, and a language picked in
the app could be missing at runtime (lint check `AppBundleLocaleChanges`).

> **Important:** a translation folder is used by Android for phones set to that language **as soon
> as it is merged**, even if the language is not yet in `SUPPORTED`. `SUPPORTED` only controls the
> in-app picker. Untranslated strings fall back to English (`skip_untranslated_strings: true` in
> `crowdin.yml`), so a partial translation shows a mix of the language and English.

## 3. Rules for code

- Never put user-visible text in a Kotlin string literal. Use `stringResource(R.string.x)` in
  Compose, `context.getString(...)` elsewhere — with the **activity** context (it carries the chosen
  locale), never the application context.
- Non-UI layers return resource ids, not text (e.g. `ImportResult.Error(@StringRes messageRes, detail)`).
  Untranslatable system text (exception messages) goes in a separate argument.
- Use positional placeholders (`%1$s`, `%1$d`) so translators can reorder them; never build a
  sentence by concatenation.
- Add a `<!-- comment -->` above a string when its context is not obvious (button size, what a
  placeholder holds): Crowdin shows it to translators.
- Not translated: `translatable="false"` strings (app name), music notation kept in code (dynamics
  `pp`…`ff`, `cresc.`, `decresc.`), glyph-only buttons (`½`, `1`, `2`, `✏️`, `🩹`, `↶`, `🗑`, `◀`,
  `▶`, `✕`, `◐`) and log messages.
- Stamps keep a language-neutral `label` and a translatable `nameRes` used as content description.
- **Changing English text**: edit the value, keep the key. Crowdin marks the translations as
  outdated and translators update them.
- **Changing the meaning** of a string: use a **new key** and delete the old one, so stale
  translations are not shown.
- **Deleting a key**: delete it in `values/strings.xml` only. Crowdin removes it from the
  translations at the next download. Until Crowdin is connected, delete it from every
  `values-*/strings.xml` too (`LanguageResourcesTest` fails otherwise).

## 4. Branch model and the `l10n_dev` branch

| Branch | Who writes | Content |
| --- | --- | --- |
| `main` | developers, through PRs | code and English source strings; receives translation PRs |
| `l10n_dev` | **only the Crowdin sync workflow** | `main` + the latest translations downloaded from Crowdin |
| feature branches | developers | code changes, new/changed English strings |

Rules for `l10n_dev`:

1. **Never commit to `l10n_dev` by hand** and never base a feature branch on it. The workflow
   rewrites it on each run; manual commits would be lost or cause conflicts.
2. Each run (daily, on a change to `values/strings.xml` on `main`, or manually) uploads the English
   source, downloads the translations, commits them to `l10n_dev` and opens — or updates — a single
   pull request **"New Crowdin translations"** into `main`, labelled `l10n`.
3. The owner reviews and merges that PR whenever convenient (see
   [10.3](#103-reviewing-a-translation-pull-request)). There is no need to merge every day: the PR
   accumulates changes until merged.
4. After merging, **delete `l10n_dev`** (GitHub offers the button on the PR). The next run recreates
   it from the current `main`, which avoids stale history and conflicts.
5. Translation fixes are made **in Crowdin**, never in the repository: a fix committed to
   `values-<lang>/strings.xml` on `main` is overwritten by the next download.

Why a `dev`-style name although the project only has `main`: it matches the AndroidAPS convention
(`l10n_dev`) and makes it obvious that the branch is a staging area. If a `dev` integration branch
is introduced later, only `pull_request_base_branch_name` in the workflow changes.

## 5. Managing languages

### 5.1 Adding a language — before Crowdin is connected

1. Create `app/src/main/res/values-<code>/strings.xml` (copy `values-es/strings.xml` and translate
   every string, or only some — missing ones fall back to English).
2. Add `<code>` to `LocaleHelper.SUPPORTED`.
3. Run the unit tests (`./gradlew :app:testDebugUnitTest`): `LanguageResourcesTest` checks the
   folder exists, that keys exist in English and are translatable, and that placeholders match.
4. Add the language to `languages_mapping` in `crowdin.yml` now (see 5.3) so that the future
   Crowdin import lands in the same folder.

### 5.2 Adding a language — once Crowdin is connected

1. In Crowdin: **Project → Settings → Languages → Target languages**, add the language.
2. In `crowdin.yml`, add the mapping from the Crowdin language id to the plain folder name, if the
   Crowdin Android code contains a region (see 5.3). Commit through a PR into `main`.
3. Translators work in Crowdin. The next workflow run brings `values-<code>/strings.xml` into the
   `l10n_dev` PR. Phones set to that language start using it once the PR is merged.
4. When the translation is complete enough to be offered (suggested: ≥ 90 %, and reviewed by a
   second speaker), add `<code>` to `LocaleHelper.SUPPORTED` in a normal PR.

### 5.3 Language codes

Crowdin's `%android_code%` adds a region for many languages (`es-rES`, `fr-rFR`, `de-rDE`,
`pt-rPT`). The `languages_mapping` block maps the **Crowdin language id** (left) to the folder
suffix (right):

```yaml
languages_mapping:
  android_code:
    es-ES: es     # Spanish → values-es
    fr: fr        # French  → values-fr
    de: de        # example: German → values-de
    pt-BR: b+pt+BR  # example of a real regional variant → values-b+pt+BR
```

Check the exact language ids in Crowdin (**Project → Settings → Languages**, or the
[Crowdin language codes list](https://support.crowdin.com/developer/language-codes/)) — a wrong id
silently produces a `values-xx-rYY` folder instead of the expected one.

### 5.4 Removing a language

1. Remove it from `LocaleHelper.SUPPORTED` (users who picked it fall back to "System default").
2. Remove it from the Crowdin target languages and from `languages_mapping`.
3. Delete its `values-<code>` folder in a PR.

## 6. Crowdin open-source license: conditions

Crowdin is free for open-source projects that meet the criteria of its
[open-source project setup request](https://crowdin.com/page/open-source-project-setup-request)
(see also [Crowdin for open source](https://crowdin.com/product/for-open-source)). Status checked
on **2026-10-11** against the public repository `github.com/musigatto/FOSScore`; re-check before
applying, as the criteria can change.

| # | Crowdin condition | Status | Evidence / what to do |
| --- | --- | --- | --- |
| 1 | A translation project has been created in Crowdin | **NOK** | Done in Phase B, before submitting the form. |
| 2 | Licensed under an OSI-approved license | **OK** | AGPL-3.0 (`LICENSE`, detected by GitHub; "AGPL v3" is in the form's list). |
| 3 | Source code publicly available for download | **OK** | Public GitHub repository. |
| 4 | No commercial products related to the project | **OK** (owner to confirm) | No ads, no paid edition, no telemetry (README). The MuPDF commercial license sold by Artifex is not a FOSScore product. |
| 5 | The applicant is the project lead | **OK only if the owner applies** | The form must be filled by the repository owner (`musigatto`), not by a contributor. |
| 6 | At least three months of work on the project | **OK** | First commit 2026-07-06 (three months reached on 2026-10-06). |
| 7 | An active community of collaborators | **Weak / NOK** | GitHub lists one contributor account; git history shows three authors. Add a `CONTRIBUTING.md`, enable Discussions, label "good first issue"s, and mention the translation effort in the README. |
| 8 | The project website's "News" section is kept up to date | **NOK** | No website (`homepage` empty). Use GitHub Releases notes or a "News" section in the README / GitHub Pages, and give that URL as "Project website URL". |
| 9 | Updated builds are released regularly | **NOK** | No GitHub release yet. Publish tagged releases with an APK on a regular schedule (e.g. monthly) before applying. |

Commitments accepted when submitting the form:

- joining the Crowdin beta group;
- contributing the project's translations to the Crowdin Global Translation Memory (which grants
  access to Crowdin's machine translation).

The form asks for: project name, project license, project website URL (optional), a detailed
project description, the applicant's email and name, and the Crowdin username (optional).

**Recommendation:** fix items 7–9 first (a few releases with notes and a visible news page), then
create the project and apply. Applying with several NOK items is likely to be refused or delayed.

## 9. Phase C — connecting Crowdin to the repository

1. **Crowdin project id**: Crowdin → project → **Tools → API** → "Project ID" (a number).
2. **Crowdin personal access token**: Crowdin → account **Settings → API → New token**; grant
   access to projects, source files and strings, and translations (read and write). Copy it once;
   it is not shown again. Never paste it in a file, issue or commit.
3. **GitHub secrets**: repository → **Settings → Secrets and variables → Actions → New repository
   secret**:
   - `CROWDIN_PROJECT_ID` = the project id;
   - `CROWDIN_PERSONAL_TOKEN` = the token.
4. **Allow the workflow to open PRs**: **Settings → Actions → General → Workflow permissions** →
   "Read and write permissions" and tick **"Allow GitHub Actions to create and approve pull
   requests"**.
5. **Check the language ids**: compare the Crowdin target language ids with `languages_mapping` in
   `crowdin.yml` (Spanish is usually `es-ES`, French `fr`). Fix them in a PR if needed.
6. **First run, with import of the existing translations**: **Actions → Crowdin sync → Run
   workflow**, tick **"Also upload the translations already in the repository"**. This sends the
   English source and the current `values-es` / `values-fr` to Crowdin so they are not lost.
7. In Crowdin, check that Spanish and French show close to 100 %. Approve the imported
   translations if "Export only approved" is enabled, otherwise they would disappear at the next
   download.
8. The run creates `l10n_dev` and the "New Crowdin translations" PR. The first one should contain no
   or only cosmetic changes (Crowdin's XML formatting); review it as in 10.3 and merge.
9. From now on, **never run the workflow with the import box ticked again**: it would overwrite work
   done in Crowdin with the repository copies.

The Crowdin **GitHub integration** (Crowdin Store app, OAuth) is an alternative to the workflow. It
uses its own service branch naming (`l10n_<branch>`); the GitHub Action was chosen because it keeps
the branch name (`l10n_dev`), the schedule and the credentials under the repository's control. Do
not enable both.

## 10. Phase D — day-to-day workflow

### 10.1 Developers

1. Add or change strings in `values/strings.xml` only, in the feature branch, following section 3.
2. The PR into `main` is reviewed as usual. Translations are not required in that PR.
3. After merge, the workflow uploads the new strings to Crowdin (push trigger), and translators are
   notified by Crowdin.

### 10.2 Translators

- Join the public Crowdin project, translate and vote/proofread there.
- Questions about context: Crowdin comments, or a GitHub issue labelled `l10n`.

### 10.3 Reviewing a translation pull request

On the "New Crowdin translations" PR from `l10n_dev`:

1. Check the diff touches only `values-*/strings.xml` (and new `values-*` folders).
2. CI / locally: `./gradlew :app:testDebugUnitTest :app:lintDebug` — `LanguageResourcesTest` catches
   broken placeholders and unknown keys; lint catches malformed XML and format errors.
3. Optionally build and switch the app language to a changed language for a quick look at long
   strings (buttons in the viewer toolbar are narrow).
4. Merge (squash is fine), then **delete `l10n_dev`**.
5. If a new language arrived and is ready, add it to `LocaleHelper.SUPPORTED` (5.2 step 4).

### 10.4 Releases

Before tagging a release, run the workflow manually and merge the pending translation PR so the
release ships the latest translations. Mention new or updated languages in the release notes (this
also feeds the "News" condition of section 6).

## 11. Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| Workflow succeeds but does nothing | Secrets missing | Phase C steps 1–3. |
| "GitHub Actions is not permitted to create or approve pull requests" | Repository setting | Phase C step 4. |
| A `values-xx-rYY` folder appears instead of `values-xx` | Missing/wrong `languages_mapping` id | Fix `crowdin.yml`, delete the wrong folder in the PR. |
| `LanguageResourcesTest` fails on placeholders | Translator changed `%1$s` | Fix the translation **in Crowdin**, re-run the workflow. |
| Translations made in Crowdin disappear | "Export only approved" with unapproved strings, or a later run with the import box ticked | Approve in Crowdin; never re-import (Phase C step 9). |
| Picked language shows English | Folder missing or language not in `SUPPORTED` / app bundle split | Check folder name, `SUPPORTED`, `enableSplit = false`. |
| Conflicts on `l10n_dev` | Manual commits or an old branch | Delete `l10n_dev`; the next run recreates it. |
