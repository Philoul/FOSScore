# CLAUDE.md

Shared guidance for anyone working on FOSScore, human or AI assistant (Claude Code reads this file
automatically; other tools can be pointed at it). Keep it short and keep it true: update it in the
same PR when a rule or command changes.

## Project

FOSScore is a FOSS sheet-music reader for Android: Kotlin, Jetpack Compose + Material 3, Room,
MuPDF (`com.artifex.mupdf:fitz`). Licence: **AGPL-3.0** (required by MuPDF), so every dependency
must be AGPL-compatible. Offline first: no telemetry, no ads, no mandatory accounts.

## Build and test

Gradle needs **JDK 17+** (Android Studio's bundled JBR works:
`JAVA_HOME=".../Android Studio/jbr"`).

```bash
./gradlew :app:assembleDebug        # build
./gradlew :app:testDebugUnitTest    # unit tests (JVM)
./gradlew :app:lintDebug            # Android lint
```

Run the unit tests before every PR. Single module (`:app`), package `com.musigatto.fosscore`.

## Code map

- `MainActivity.kt`: navigation (`Screen` sealed interface). `FOSScoreApp.kt`: manual dependency
  container (database, repositories, application scope).
- `library/`: Room database (`AppDatabase`, schema version 4), entities, DAOs, repositories,
  `SheetImporter`.
- `pdf/MuPdfDoc.kt`: MuPDF wrapper. Its API is **not thread-safe**: callers serialize access with a
  `Mutex`.
- `ui/library/`: library and sheet-detail screens.
- `ui/viewer/`: `PdfViewerScreen.kt` (large; see the roadmap) plus pure helpers `PageFlow`,
  `ZoomMath`, `InkGeometry`, `StampGeometry`.
- `docs/superpowers/`: feature specs and plans. `docs/architecture-roadmap.md`: known issues and the
  improvement plan.

## Rules

**User data is sacred.**
- Every Room schema change needs a version bump **and** a migration. Never rely on a destructive
  fallback to ship a schema change.
- Writes that span several statements or tables (undo, delete) run in one transaction.
- Deleting a sheet deletes everything attached to it (stamps, strokes, file).

**Keep logic testable.**
- Put non-UI logic in pure functions or classes (like `PageFlow`, `ZoomMath`) and unit-test it.
- A bug fix adds a test that fails before the fix whenever the code is testable.
- Do not grow `PdfViewerScreen.kt`. New behaviour goes into its own file or composable.

**Pull requests.**
- One topic per PR: bug fix, refactor and feature are separate PRs. Aim for under ~300 changed
  lines.
- A refactor PR does not change behaviour, and says so.
- Branch from the current `main`. Names: `fix/…`, `feature/…`, `docs/…`, `refactor/…`.
- Before touching `PdfViewerScreen.kt`, check open issues and PRs: it is the main conflict hot spot.

**Style.**
- Follow the surrounding code: naming, comment density, Compose idioms.
- Comments explain *why*. The `ponytail:` prefix marks a deliberate shortcut and its upgrade path.
- User-facing text goes in string resources, not in Kotlin literals.
- Language of comments, commits and PRs: *to be agreed by the maintainer* (see roadmap step 0.2).

**Secrets and privacy.**
- Never commit keystores, signing passwords, API tokens or `local.properties`.
- Never commit users' PDFs, exported libraries or device logs containing personal data.

## Using AI assistants

- The human who opens a PR is responsible for it: read and understand every line, and run the build
  and tests before asking for review.
- Say in the PR description when a significant part was generated by an AI tool.
- Prefer plan, then implement for non-trivial work: write the plan in `docs/superpowers/` (or an
  issue) and get agreement before large changes.
- An assistant must not push, merge, force-push or publish releases without an explicit request
  from the human.
- Do not paste secrets or personal data (users' scores, logs with names or emails) into AI tools.
