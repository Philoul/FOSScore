# Internationalization (i18n)

Development log and reference for translating FOSScore. Everything in this work stream — code,
comments, string keys, commit messages, branch names and this document — is written in English.

- **Branch:** `feature/i18n-string-resources` (from `main`)
- **Status:** first pass done — all user-facing strings extracted, English default, Spanish and
  French translations, in-app language picker.

## Goals

1. No user-facing text hardcoded in Kotlin: every string lives in `res/values*/strings.xml`.
2. English is the default language (`values/`); other languages are translation folders.
3. The app language follows the phone by default and can be overridden in the app, the same way
   AndroidAPS does it.
4. Translation folders can later be synchronized with Crowdin.

## Layout

```
app/src/main/res/
  values/strings.xml       English, default and Crowdin source
  values-es/strings.xml    Spanish (taken from the strings previously hardcoded in the code)
  values-fr/strings.xml    French
crowdin.yml                Crowdin mapping for the folders above
```

Plain language folders (`values-es`, not `values-es-rES`) are used on purpose: they also cover
regional variants of the phone language (es-MX, fr-CA…). A real regional variant, if ever needed,
uses the BCP 47 folder form `values-b+pt+BR`.

## How the language is chosen

Modelled on AndroidAPS' `LocaleHelper` (`core/ui/.../locale/LocaleHelper.kt` in AAPS):

| Piece | Role |
| --- | --- |
| `locale/LocaleHelper.kt` | `SUPPORTED` language list, reads the preference, builds the locale, `wrap(context)` |
| `Settings.language` / `setLanguage` | Preference `language` in `fosscore_settings`; `"default"` = follow the phone |
| `MainActivity.attachBaseContext` | Wraps the base context with the chosen locale |
| `MainActivity.changeLanguage` | Stores the new choice and calls `recreate()` |
| `LibraryScreen` → `LanguageMenu` | Picker in the library header: "System default" + one entry per supported language |

Behaviour:

- **Default (`"default"`)** — the context is not touched; Android resolves resources from the
  phone's language list. If the phone language is not translated, English is shown.
- **Explicit choice** — `wrap()` creates a configuration context with that locale, so all resource
  lookups in the activity (Compose `stringResource` included, and Material's own strings) use it.
  `Locale.setDefault` is updated too, so numbers and `String.format` match the UI language.
- Going back to "System default" restores the phone locale read from
  `Resources.getSystem().configuration`, not from `Locale.getDefault()` (which `wrap()` overwrites).
- Language names in the picker are autonyms built from `Locale.getDisplayName(locale)` ("Español",
  "Français"), so adding a language needs no extra string.

Differences from AndroidAPS:

- Only `Configuration.setLocale` is used (the single-locale form), no `LocaleList`.
- No "simple mode" override and no `dk` → `da` fix-up: the list only holds valid BCP 47 tags.
- There is no settings screen yet, so the picker sits in the library header.

App Bundles: `bundle { language { enableSplit = false } }` in `app/build.gradle.kts`. Without it,
Google Play would only install the translations matching the phone's languages, and a language
picked in the app could be missing at runtime (lint check `AppBundleLocaleChanges`).

## Rules for code

- Never put user-visible text in a Kotlin string literal. Use `stringResource(R.string.x)` in
  Compose, `context.getString(...)` elsewhere — with the **activity** context (it carries the chosen
  locale), not the application context.
- Non-UI layers return resource ids, not text (e.g. `ImportResult.Error(@StringRes messageRes, detail)`).
  Untranslatable system messages (exception text) are passed as a separate argument.
- Use positional placeholders (`%1$s`, `%1$d`) so translators can reorder them; never build a
  sentence by concatenating strings.
- Text that must not be translated (app name, music notation) is either `translatable="false"` or
  stays in code when it is notation, not language: dynamics `pp`…`ff`, `cresc.`, `decresc.`, and the
  glyph-only buttons (`½`, `1`, `2`, `✏️`, `🩹`, `↶`, `🗑`, `◀`, `▶`, `✕`, `◐`).
- Stamps keep a language-neutral `label` and get a translatable `nameRes` used as content
  description.
- Log messages are not user-facing and are not extracted.

## Adding a language

1. Add the tag to `LocaleHelper.SUPPORTED`.
2. Add `values-<code>/strings.xml` (or let Crowdin create it, see below).
3. Run the unit tests: `LanguageResourcesTest` checks that every supported language has a folder,
   that translations only use keys that exist in `values/` and are translatable, and that
   placeholders match the English source.

## Crowdin (not connected yet)

`crowdin.yml` maps `values/strings.xml` to `values-%android_code%/strings.xml`, with
`languages_mapping` turning Crowdin's regional codes back into plain folders (`es-ES` → `es`,
`fr` → `fr`). Credentials are read from `CROWDIN_PROJECT_ID` and `CROWDIN_PERSONAL_TOKEN`; never
commit them.

To verify when the Crowdin project is created:

- [ ] Crowdin language ids for the target languages (each new language needs a `languages_mapping` entry).
- [ ] Upload the existing `values-es` / `values-fr` files as initial translations
      (`crowdin upload translations`) so they are not lost on the first download.
- [ ] Decide whether a language appears in the picker before it is complete (currently: only
      after it is added to `SUPPORTED`).
